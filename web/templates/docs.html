1. Overview

Duckway is an API proxy that manages real API keys centrally. AI agents and other clients never see real keys — they use phantom tokens that look identical in format but are swapped for real keys by the proxy.

  • No key leakage — agents only have fake keys; real keys never leave the server
  • ACL system — 22 pre-built templates from official API docs + custom JSON rules
  • Approval workflow — require admin consent with configurable TTL, approve via Discord/Telegram
  • HTTPS MITM proxy — transparent interception with auto-generated TLS certificates
  • Key groups — round-robin, least-used, failover to avoid rate limits
  • 16 canary token types — auto-deployed honeypots detect compromised machines
  • Audit trail — filterable request log with client, service, key, status

Admin setup

  2. Default services pre-configured: OpenAI, Anthropic, GitHub, Discord, Telegram
  3. API Keys → add your real keys (encrypted at rest)

4. Services & API Keys

A Service = an upstream API. Each service configures:

NameSlug for proxy URL: /proxy/{name}/...
Upstream URLe.g., https://api.openai.com
Auth Typebearer, header, or query
Key Prefix + LengthFor phantom token format matching (e.g., sk-, 164 chars)
Key DirectoryWhere keys are deployed on client (e.g., ~/.config/openai/credentials)
Default ACLService-level access control — applies to all keys unless overridden

API Keys are your real credentials, stored AES-256-GCM encrypted. Each key can have its own ACL. Edit name, rotate the key value, or change ACL from the API Keys page.

5. ACL System

Three-layer access control. Request must pass ALL non-empty layers — each can only narrow, never widen:

  1. Service default_acl — widest scope, applies to all keys in service
  2. API Key acl — narrows further per real key
  3. Phantom Token permission_config — narrowest, per client+service

Example: Service allows all OpenAI endpoints. Key restricts to chat + embeddings. Phantom token restricts to gpt-4o-mini only. An agent using this phantom token can only call chat completions with gpt-4o-mini — the intersection of all three layers.

Pre-built templates (22)

ServiceTemplates
OpenAIallow-all, chat-only, chat-embeddings, inference-all, no-admin
Anthropicallow-all, messages-only, no-batches
GitHuballow-all, read-only, repo-read, issues-prs, no-destructive, gists-only
Discordallow-all, webhook-only, messages-only, read-only
Telegramallow-all, send-only, read-only, no-admin

Custom ACL JSON

{
  "version": "1",
  "rules": [{
    "name": "chat-only",
    "endpoints": [
      {"method": "POST", "path": "/v1/chat/completions", "allow": true,
       "constraints": {"body": {"model": {"oneOf": ["gpt-4o-mini"]}, "max_tokens": {"max": 1024}}}},
      {"method": "GET", "path": "/v1/models", "allow": true}
    ],
    "rate_limit": {"requests_per_minute": 60},
    "deny_all_other": true
  }]
}

Constraints: oneOf (string match), max/min (numeric), forbidden (field must not exist). Path wildcards: /v1/files/*

6. Client Setup

Each machine registers as a Client with a unique name and 6-char short ID (e.g., k7x2m9). The short ID tags canary emails for per-machine alerting.

Registration

  1. Admin creates client → gets token + full setup command
  2. On the machine: curl -fsSL http://server/install.sh | sh && duckway init
  3. Client downloads CA cert, installs to system trust store
  4. Admin assigns API keys → phantom tokens generated
  5. duckway sync → keys in ~/.duckway/keys.env + canary files deployed

Per-client settings

Canary: ON/OFFToggle canary token deployment per client
Phantom tokensEach editable: env name, key path, approval, TTL
Canary tokensView deployed tokens, links to canarytokens.org management

Refreshable tokens are stored as API keys with encrypted access + refresh tokens. Upload formats vary by provider:

# Generic OAuth token response
jq -r '[.access_token, .refresh_token, (.expires_in // 0)] | @tsv' token-response.json

8. Proxy Modes

Mode 1: HTTPS Proxy (transparent)

export HTTPS_PROXY=http://localhost:18080
curl https://api.openai.com/v1/chat/completions ...
# → duckway client (MITM) → server → key injection → upstream

Client generates per-host TLS certs signed by Duckway CA. Known service hosts are intercepted; unknown hosts tunnel through transparently.

Mode 2: Direct URL (lightweight)

curl http://duckway-server/proxy/openai/v1/chat/completions \
  -H "X-Duckway-Token: <token>" ...

No CA cert needed. Works as an OpenAI-compatible endpoint.

Heartbeat

Built-in /proxy/heartbeat/ping service. Every client auto-gets a heartbeat key. duckway status tests it.

9. Approval Workflow

  1. Agent request → 403 duckway_approval_pending
  2. Notification sent to Discord/Telegram with approval ID
  3. Admin approves: click ✅ reaction (Discord), tap button (Telegram), or !approve <id>
  4. Approval valid for the configured TTL (default 24h)
  5. After TTL expires → needs re-approval

TTL is per-phantom-token, editable from the Clients page. Set to 0 to disable approval entirely.

13. Control Channels (Discord)

A Control Channel (CC) binds one client to one Discord category via a bot. Inside that category every channel maps to an agent session — when a human posts a message, an on-machine daemon runs Claude Code or Codex and posts the response back. A separate "management" channel accepts text commands like !new for opening new task channels.

Mental model (CC v2)

ConceptWhat it isWhere it lives
Bot tokenThe Discord bot's API keyEncrypted in api_keys
CC{bot, guild_id, category_id, client_id, agent_type} — 1:1 with a clientcontrol_channels table
Management channelAuto-created at CC create, named <client>-control. Accepts !cmd.cc_channels (kind=management)
Task channelCreated by !new or the MCP discord_create_task_channel tool. One per agent session.cc_channels (kind=task)
Session idThe agent's resume/thread handle for the channel; persisted by the daemon~/.duckway/cc-sessions.json on the agent
HandleOpaque dwch_… id the agent + daemon seeMaps to real channel_id server-side

Real Discord IDs (channel_id, guild_id, category_id) never leave the server. Agents and the daemon only hold opaque handles.

Discord bot setup (one-time, ~10 min)

This part isn't duckway-specific — you do it at discord.com/developers/applications.

  1. Create the bot. New Application → name it → left sidebar Bot → click Reset Token → copy the token now (shown once). Treat like a password.
  2. Flip privileged intents. Same page, scroll to Privileged Gateway Intents:
    • ✅ Message Content Intent — required (without it, message bodies arrive empty)
    • ✅ Server Members Intent — optional, only if you'll use required_reactors on approvals
  3. Invite the bot. Duckway generates the Discord OAuth URL from the saved bot token in the Control Channel create form. It requests Manage Channels, Manage Roles, View Channel, Send Messages, Add Reactions, and Read Message History. Use that URL to pick the guild and authorize the bot.
  4. Lock down to one category (recommended). Use Grant bot access in Duckway to write a category permission override. After setup, you can narrow guild-wide role permissions by unchecking Manage Channels and Manage Roles globally. If Discord rejects the automatic grant, right-click the target category → Edit Category → Permissions → add the bot with the runtime perms above. Now a leaked token's blast radius is one category, not the guild.
  5. Select the destination in Duckway. Click Load Discord setup; Duckway lists servers the bot can see and categories in the selected server. Pick a category and click Grant bot access, or create a category and Duckway attempts the grant automatically. Then click Check permissions to verify create/send/react/read/delete access before saving. Manual IDs are only needed for fallback/debugging:
    • guild_id = right-click your guild icon → Copy Server ID
    • category_id = right-click the category header → Copy Channel ID (Discord internally treats categories as channels with type=4)

Admin one-time setup (in duckway)

  1. API Keys → add the bot token from above. Service discord.
  2. Control Channels → New CC → fill name + pick client + agent type (claude_code or codex) + the bot, then use the Discord setup wizard to invite/load/select the server and category. On save, duckway provisions <client>-control under the category and issues a phantom bot token bound to that client. If a step fails, the create rolls back and tells you which one.
  3. Click into the CC → Test (create + delete channel) to verify the bot can do its job before pointing real workloads at it.
  4. Clients with a CC show a one-line summary on their detail page; the full state (channels, sessions) lives on the CC detail.

Agent end (the user's machine)

# Pull state + write Claude Code / Codex MCP config
duckway sync
# Run the watcher (foreground, for testing)
duckway cc watch
# Or as a systemd user unit (Linux):
mkdir -p ~/.config/systemd/user/
cp examples/duckway-cc-watch.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now duckway-cc-watch

Security boundary

  • Bot token = the only real boundary. Two CCs sharing a bot can technically reach each other's channels. Use different bots to isolate teams/projects.
  • Path-level ACL rejects cross-CC handles: any {handle} in a request must belong to the caller's CC (HTTP 403 otherwise).
  • Phantom token is bound to (client, bot, CC) — placeholder_keys.env_name is DUCKWAY_CC_<cc_id> so each (client, CC) gets its own row even when the bot is shared.
  • Agent execution: claude_code passes --dangerously-skip-permissions to claude; codex uses codex exec --json --sandbox workspace-write. When tmux is installed, supported agents run in attachable duckway-<handle> sessions. Trust the channel — anyone in the Discord category can drive the agent.

Inbox runtime

A server-side WSS gateway holds one connection per unique bot token. MESSAGE_CREATE / UPDATE / DELETE + CHANNEL_DELETE + MESSAGE_REACTION_ADD events get filtered by the cc_channels cache, written to discord_inbox, and pushed live via the SSE hub to any connected daemon.

Tunable via Settings:

KeyDefault
cc_inbox_retention_hours24
cc_inbox_max_per_channel1000
cc_inbox_cleanup_interval_minutes10

Test/dev: DUCKWAY_CC_DISABLE_GATEWAY=1 skips the WSS dial. DUCKWAY_CC_DEBUG_INJECT=1 exposes POST /api/cc/{id}/inject_event for synthetic events (used by the e2e suite).

Lifecycle

  • Delete CC → every channel under it is best-effort archived first, the row is dropped (cascades cc_channels), and the phantom token is removed.
  • User deletes a Discord channel manually → CHANNEL_DELETE arrives → server drops cc_channels row + publishes channel_delete via SSE → daemon clears the session id from cc-sessions.json.
  • !end from inside a task channel posts a farewell, archives the Discord channel, drops the cc_channels row, fires the same SSE event.

Agent types

claude_code and codex are wired. Both use tmux when available and fall back to headless mode with --no-tmux or when tmux is missing. The schema still reserves openclaw, harmes, cursor, copilot_cli; those store the assignment and log writer not implemented yet.

Tailscale Integration

Production compose uses Tailscale sidecar containers. Each service shares its network stack with the Tailscale container via network_mode: "service:ts-*". Tailscale terminates HTTPS and forwards plain HTTP to the service.

Zero ports exposed to host or LAN. Only accessible via Tailscale.
