1. Overview

Duckway is an API proxy that manages real API keys centrally. AI agents and other clients never see real keys — they use phantom tokens that look identical in format but are swapped for real keys by the proxy.

  • No key leakage — agents only have fake keys; real keys never leave the server
  • ACL system — 22 pre-built templates from official API docs + custom JSON rules
  • Approval workflow — require admin consent with configurable TTL, approve via Discord/Telegram
  • HTTPS MITM proxy — transparent interception with auto-generated TLS certificates
  • Key pools — per-request rotation or quota-aware leases to avoid rate limits; Key bundles assign several services' keys to a client at once
  • 16 canary token types — auto-deployed honeypots detect compromised machines
  • Audit trail — filterable request log with client, service, key, status

3. Quick Start

Docker (recommended)

# Production
cp -n .env.example .prod.env && chmod 600 .prod.env
./scripts/prod.sh up

# Development (auto-seeds test data)
./scripts/dev.sh up

One-liner client install

curl -fsSL http://duckway-server:8080/install.sh | sh
duckway init

Admin setup

  1. Login — credentials shown in server log on first run (dev mode: duckway/duckway)
  2. Default services pre-configured: OpenAI, Anthropic, xAI/Grok, GitHub, Discord, Telegram
  3. Credentials → add your real keys (encrypted at rest)
  4. Clients → register a machine → copy the full setup command
  5. Assign keys to the client → phantom tokens auto-generated
  6. Optionally: set ACL, configure canary tokens, add notification channels

4. Services & API Keys

A Service = an upstream API. Each service configures:

NameSlug for proxy URL: /proxy/{name}/...
Upstream URLe.g., https://api.openai.com
Auth Typebearer, header, or query
Key Prefix + LengthFor phantom token format matching (e.g., sk-, 164 chars)
Key DirectoryWhere keys are deployed on client (e.g., ~/.config/openai/credentials)
Default ACLService-level access control — applies to all keys unless overridden

Credentials (static API keys, refreshable tokens and GitHub Apps) are your real secrets, stored AES-256-GCM encrypted. Each key can have its own ACL. Edit name, rotate the key value, or change rules from the Credentials page.

For Grok Build, add the real xAI API key under service xai and assign it to clients as XAI_API_KEY. duckway sync writes the phantom token into ~/.grok/config.toml for grok-4.5; Grok traffic to cli-chat-proxy.grok.com then routes through Duckway and the real key stays server-side.

5. ACL System

Three-layer access control. Request must pass ALL non-empty layers — each can only narrow, never widen:

  1. Service default_acl — widest scope, applies to all keys in service
  2. API Key acl — narrows further per real key
  3. Phantom Token permission_config — narrowest, per client+service

Example: Service allows all OpenAI endpoints. Key restricts to chat + embeddings. Phantom token restricts to gpt-4o-mini only. An agent using this phantom token can only call chat completions with gpt-4o-mini — the intersection of all three layers.

Pre-built templates (22)

ServiceTemplates
OpenAIallow-all, chat-only, chat-embeddings, inference-all, no-admin
Anthropicallow-all, messages-only, no-batches
GitHuballow-all, read-only, repo-read, issues-prs, no-destructive, gists-only
Discordallow-all, webhook-only, messages-only, read-only
Telegramallow-all, send-only, read-only, no-admin

Custom ACL JSON

{
  "version": "1",
  "rules": [{
    "name": "chat-only",
    "endpoints": [
      {"method": "POST", "path": "/v1/chat/completions", "allow": true,
       "constraints": {"body": {"model": {"oneOf": ["gpt-4o-mini"]}, "max_tokens": {"max": 1024}}}},
      {"method": "GET", "path": "/v1/models", "allow": true}
    ],
    "rate_limit": {"requests_per_minute": 60},
    "deny_all_other": true
  }]
}

Constraints: oneOf (string match), max/min (numeric), forbidden (field must not exist). Path wildcards: /v1/files/*

6. Client Setup

Each machine registers as a Client with a unique name and 6-char short ID (e.g., k7x2m9). The short ID tags canary emails for per-machine alerting.

Registration

  1. Admin creates client → gets token + full setup command
  2. On the machine: curl -fsSL http://server/install.sh | sh && duckway init
  3. Client downloads CA cert, installs to system trust store
  4. Admin assigns API keys → phantom tokens generated
  5. duckway sync → keys in ~/.duckway/keys.env + canary files deployed

GitHub App Repo Scope

GitHub App installation minter keys are uploaded once under Credentials (type GitHub App). Repo access is assigned directly from Clients → Assign Key: choose the GitHub App minter key, select available repositories from the repo selector when Duckway can list them, or enter allowed repositories manually as OWNER/REPO, then pick deploy pull-only or development pull/push mode.

Duckway stores this as the placeholder's permission_config. The proxy checks the ACL before minting and then asks GitHub for a short-lived installation token scoped only to the repository parsed from the Git/API path.

Refreshable Token Upload Formats

Refreshable tokens are stored as API keys with encrypted access + refresh tokens. Upload formats vary by provider:

ProviderWhat to pasteHow to get it
Claude Code{"claudeAiOauth":{"accessToken":"...","refreshToken":"...","expiresAt":...}}Run claude login, then copy ~/.claude/.credentials.json
Generic OAuth{"access_token":"...","refresh_token":"...","expires_in":3600}Copy the provider token endpoint response or extract with jq
ManualAccess token, refresh token, token endpoint, optional Unix-ms expiryCopy values from the provider CLI, dashboard, or saved token JSON

Deleting a refreshable token first shows impacted Key bundles, clients, and Control Channels. Confirming removes suite entries, unassigns client phantom tokens, and disables affected Control Channels in red until a replacement bot token is assigned.

# Claude local credentials
jq -r '.claudeAiOauth | [.accessToken, .refreshToken, (.expiresAt // 0)] | @tsv' ~/.claude/.credentials.json

# Generic OAuth token response
jq -r '[.access_token, .refresh_token, (.expires_in // 0)] | @tsv' token-response.json

8. Proxy Modes

Mode 1: HTTPS Proxy (transparent)

export HTTPS_PROXY=http://localhost:18080
curl https://api.openai.com/v1/chat/completions ...
# → duckway client (MITM) → server → key injection → upstream

Client generates per-host TLS certs signed by Duckway CA. Known service hosts are intercepted; unknown hosts tunnel through transparently.

Mode 2: Direct URL (lightweight)

curl http://duckway-server/proxy/openai/v1/chat/completions \
  -H "X-Duckway-Token: <token>" ...

No CA cert needed. Works as an OpenAI-compatible endpoint.

Heartbeat

Built-in /proxy/heartbeat/ping service. Every client auto-gets a heartbeat key. duckway status tests it.

9. Approval Workflow

  1. Agent request → 403 duckway_approval_pending
  2. Notification sent to Discord/Telegram with approval ID
  3. Admin approves: click ✅ reaction (Discord), tap button (Telegram), or !approve <id>
  4. Approval valid for the configured TTL (default 24h)
  5. After TTL expires → needs re-approval

TTL is per-phantom-token, editable from the Clients page. Set to 0 to disable approval entirely.

10. Key pools & Load Balancing

The Key pools page (/admin/key-pools) holds two kinds of pool. Per-request rotation pools pick a member for every request using the strategies below; phantom tokens and key bundles point at them. Quota-aware lease pools lease a key to a client by remaining quota and move on when the client reports it exhausted.

StrategyBehavior
round-robinCycles through keys in order
least-usedPicks key with lowest usage count
failoverUses first active key; falls back to next

12. Notifications & Interactive Approval

Channels

No public endpoints needed — Discord uses outbound WSS, Telegram uses outbound HTTP long-polling.

What triggers a notification

An alert is sent to every enabled channel when an agent request needs approval and none is on file: a proxied API call through a phantom token that requires approval, or a key loan (LOAN) for a binding that requires approval. The message carries the approval ID, client, service, method and path. Nothing else is sent today (canary alerts use the canary email, not these channels).

Managing channels

Each channel has an Enabled switch, Edit, Test and Delete. A disabled channel receives no alerts. Secrets (bot tokens, webhook URLs, shared secrets) are never sent back to the browser: the Edit form shows them as masked, and leaving a masked field untouched keeps the stored value. Test sends a message through the saved settings; save edits first.

13. Control Channels (Discord)

A Control Channel (CC) binds one client to one Discord category via a bot. Inside that category every channel maps to an agent session — when a human posts a message, an on-machine daemon runs Claude Code or Codex and posts the response back. A separate "management" channel accepts text commands like !new for opening new task channels.

Mental model (CC v2)

ConceptWhat it isWhere it lives
Bot tokenThe Discord bot's API keyEncrypted in api_keys
CC{bot, guild_id, category_id, client_id, agent_type} — 1:1 with a clientcontrol_channels table
Management channelAuto-created at CC create, named <client>-control. Accepts !cmd.cc_channels (kind=management)
Task channelCreated by !new or the MCP discord_create_task_channel tool. One per agent session.cc_channels (kind=task)
Session idThe agent's resume/thread handle for the channel; persisted by the daemon~/.duckway/cc-sessions.json on the agent
HandleOpaque dwch_… id the agent + daemon seeMaps to real channel_id server-side

Real Discord IDs (channel_id, guild_id, category_id) never leave the server. Agents and the daemon only hold opaque handles.

Discord bot setup (one-time, ~10 min)

This part isn't duckway-specific — you do it at discord.com/developers/applications.

  1. Create the bot. New Application → name it → left sidebar Bot → click Reset Token → copy the token now (shown once). Treat like a password.
  2. Flip privileged intents. Same page, scroll to Privileged Gateway Intents:
    • ✅ Message Content Intent — required (without it, message bodies arrive empty)
    • ✅ Server Members Intent — optional, only if you'll use required_reactors on approvals
  3. Invite the bot. Duckway generates two Discord OAuth URLs from the saved bot token. Invite bot requests Manage Channels, View Channel, Send Messages, Add Reactions, and Read Message History. Setup invite additionally requests Manage Roles so Duckway can write category permission overrides.
  4. Lock down to one category (recommended). Use Grant bot access in Duckway to write a category permission override. After setup, you can narrow guild-wide role permissions by unchecking Manage Channels and, if used, Manage Roles globally. If Discord rejects the automatic grant, use Setup invite or right-click the target category → Edit Category → Permissions → add the bot with the runtime perms above. Now a leaked token's blast radius is one category, not the guild.
  5. Select the destination in Duckway. Click Load Discord setup; Duckway lists servers the bot can see and categories in the selected server. Pick a category and click Grant bot access, or create a category and Duckway attempts the grant automatically. Then click Check permissions to verify create/send/react/read/delete access before saving. Manual IDs are only needed for fallback/debugging:
    • guild_id = right-click your guild icon → Copy Server ID
    • category_id = right-click the category header → Copy Channel ID (Discord internally treats categories as channels with type=4)

Admin one-time setup (in duckway)

  1. Credentials → add the bot token from above. Service discord.
  2. Control Channels → New CC → fill name + pick client + agent type (claude_code, codex, or openclaw) + the bot, then use the Discord setup wizard to invite/load/select the server and category. On save, duckway provisions <client>-control under the category and issues a phantom bot token bound to that client. If a step fails, the create rolls back and tells you which one.
  3. Click into the CC → Test (create + delete channel) to verify the bot can do its job before pointing real workloads at it.
  4. Clients with a CC show a one-line summary on their detail page; the full state (channels, sessions) lives on the CC detail.

Agent end (the user's machine)

# Pull state + write Claude Code / Codex MCP config
duckway sync
# Run the watcher (foreground, for testing)
duckway cc watch
# Or as a systemd user unit (Linux):
mkdir -p ~/.config/systemd/user/
cp examples/duckway-cc-watch.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now duckway-cc-watch
journalctl --user -u duckway-cc-watch -f

Daemon needs the selected agent binary (claude, codex, or openclaw) in $PATH. Codex always uses Duckway's local duckway-openai provider and OPENAI_API_KEY placeholder. When the assigned OpenAI key is Codex OAuth, Duckway writes a fake ~/.codex/auth.json, intercepts auth.openai.com/oauth/token refreshes, and swaps the real refresh token only at the gateway. OpenAI Platform API keys must allow api.responses.write. OpenClaw uses openclaw agent --message-file --json with agent id from DUCKWAY_CC_OPENCLAW_AGENT or default. Per-channel cwd defaults to ~/.duckway/cc-workspace/<handle>/ (auto-created); override with !new --cwd /path. For launch debugging, use duckway cc watch --debug or DUCKWAY_CC_DEBUG=1 duckway cc watch -d; logs include agent type, runner mode, sandbox/permission fields, and sanitized argv with only prompt head/tail.

Security boundary

  • Bot token = the only real boundary. Two CCs sharing a bot can technically reach each other's channels. Use different bots to isolate teams/projects.
  • Path-level ACL rejects cross-CC handles: any {handle} in a request must belong to the caller's CC (HTTP 403 otherwise).
  • Phantom token is bound to (client, bot, CC) — placeholder_keys.env_name is DUCKWAY_CC_<cc_id> so each (client, CC) gets its own row even when the bot is shared.
  • Agent execution: claude_code passes --dangerously-skip-permissions to claude; codex uses a per-CC sandbox enum (workspace-write, read-only, danger-full-access, or none) validated by both server and client; openclaw uses openclaw agent --session-key duckway:<handle> --message-file <file> --json. Control Channels never send free-form CLI arguments to the client. When tmux is installed, Claude/Codex run in attachable <handle>-duckway sessions. Trust the channel — anyone in the Discord category can drive the agent.

Inbox runtime

A server-side WSS gateway holds one connection per unique bot token. MESSAGE_CREATE / UPDATE / DELETE + CHANNEL_DELETE + MESSAGE_REACTION_ADD events get filtered by the cc_channels cache, written to discord_inbox, and pushed live via the SSE hub to any connected daemon.

Codex tmux turns are allowed to run past five minutes for long-running prompts such as /goal. The channel stays busy and the final reply is posted when Codex writes its completion event.

Tunable via Settings:

KeyDefault
cc_inbox_retention_hours24
cc_inbox_max_per_channel1000
cc_inbox_cleanup_interval_minutes10

Test/dev: DUCKWAY_CC_DISABLE_GATEWAY=1 skips the WSS dial. DUCKWAY_CC_DEBUG_INJECT=1 exposes POST /api/cc/{id}/inject_event for synthetic events (used by the e2e suite).

Lifecycle

  • Delete CC → every channel under it is best-effort archived first, the row is dropped (cascades cc_channels), and the phantom token is removed.
  • User deletes a Discord channel manually → CHANNEL_DELETE arrives → server drops cc_channels row + publishes channel_delete via SSE → daemon clears the session id from cc-sessions.json.
  • !end from inside a task channel posts a farewell, archives the Discord channel, drops the cc_channels row, fires the same SSE event.

Agent types

claude_code, codex, and openclaw are wired. Claude/Codex use tmux when available and fall back to headless mode with --no-tmux or when tmux is missing. OpenClaw runs headless through the OpenClaw CLI. The schema still reserves harness, cursor, copilot_cli; those store the assignment and log writer not implemented yet.

Tailscale Integration

Production compose uses unprivileged userspace Tailscale sidecars. Each app shares its sidecar network namespace and listens only on loopback; Tailscale forwards tailnet TCP port 80 to that listener without certificate-domain or HTTP Host matching.

No host ports, /dev/net/tun, or added Linux capabilities are required. In split mode, use separate tagged admin and gateway auth keys with a deny-by-default Headscale policy; hostnames are not security identities.

Also new

  • Command palette. Press Ctrl+K (⌘K on a Mac), or use the Search row at the top of the sidebar (the Search button in the top bar on narrow screens), to jump to any page or find a client, credential, key pool, bundle, phantom token, service or notification channel by name.
  • Approve rules. Phantom-token ACL rules can route a matching request into the approval flow instead of allowing or denying it.
  • Stricter browser policy. The console enforces Trusted Types and a nonce-only script policy.

Upgrade notes

  • Old approvals were expired. Approvals recorded by earlier versions with a relative expiry never ran out. They were expired when you upgraded, so an affected token asks for approval again.
  • A rule approval covers one exact request. Approving a held request releases that method, path, query string and body for the approval time-to-live. Any change to one of them asks again. The approval shows the query and a short keyed hash of the body.
  • Encoded slashes need a per-service switch. A request path containing %2F is refused (400) unless the service has Allow encoded slashes turned on in its Delivery settings (for example GitLab project paths). %5C, an encoded ? or # (%3F, %23) and control characters in a path are always refused.
  • Behind a proxy that rewrites Host, set DUCKWAY_PUBLIC_ORIGIN. Admin writes are accepted only from the console's own origin. Either forward the original Host (proxy_set_header Host $host;) or set DUCKWAY_PUBLIC_ORIGIN to the public origin, for example https://console.example.com.
  • Changing the admin password signs out other sessions. The session you changed it from stays signed in.
  • Existing clients keep working. Already-installed duckway clients register and log in as before; they send no browser headers, which the admin API still accepts.
